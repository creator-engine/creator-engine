# Research Handoff — IaC deployment path for CE's Autonomous-Fleet dev setup to OTHER projects

**Requested by:** Operator (2026-06-30) · **Model:** Opus, high effort · **Role:** architect_research (READ-ONLY; return a decision-grade architecture + roadmap; no code changes)
**Decision owner:** Operator (this informs ratification + a build program)

## Frame
CE's INTERNAL development setup — **Autonomous Fleet + CEO/strangeLoop** (multiple codex controller/worker seats + governed orchestration + the gate machinery) — has proven itself: ~10 days of it produced an unprecedented rise in commits / PRs / LOC in the `creator-engine` repo. The Operator now wants to **deploy this exact fleet setup to OTHER projects** he works on, to get the same dev throughput — but **fully ISOLATED** from CE-internal development (zero mixing). **CE has no IaC path for fast (~one-click) deployment** of the fleet. Design that path.

## Locked decisions (Operator, 2026-06-30 — build to these, don't re-open)
1. **Target infra = a FRESH ISOLATED cloud instance per project** (clean per-project VM, provisioned from scratch; leverages the AWS/GCP credits). IaC = cloud-init/Terraform-class + the existing container stack. Physical isolation is the chosen isolation primitive.
2. **Framing = product-aware, internal-first.** Solve the Operator's other-projects need NOW, but architect it as the foundation of the **productizable "CE Autonomous Fleet" offering** (aligned with the NVIDIA-pitch direction: containerized CE + live users). Same artifact; design for generality so internal use doubles as the product foundation.
3. **Tiered, one IaC path with a tier knob:** a **lean single-controller Solo+CEO** variant (cheap, one contained controller, no multi-seat fan-out) AND the **full multi-seat Autonomous Fleet** (parallel throughput). The deployment path selects tier via a manifest knob.

## What to deliver (decision-grade)
1. **Decompose "the fleet" into deployable components.** Enumerate everything that constitutes the internal setup and must be reproduced per project: the controller/orchestrator + N worker/controller seats; the **containment substrate** (herdr fork, bwrap+Landlock, gVisor/runsc, the codex-runsc base image); the **governed orchestration** machinery (dispatch→implementer-in-worktree→harvest→independent-review→merge-gate, the `ce`/cev3 Scope lifecycle, `validate-pr` gates, carriers, work-class gates); **identity/credential infra** (per-seat PATs, the GitHub App, OpenBao secret broker, the identity-registry SSOT); forge-as-hub + merge queue + board/seat monitors + watchers + the crons (seat-check / poll-devs / conveyor-tend); the **brain/recall** (optional leg); SSOT artifacts. For EACH: classify as **project-specific (must be templatized per deployment)** vs **shared/infra (provisioned once per VM)**.
2. **Map EXISTING primitives vs the GAP (reuse-before-reinvent — hard requirement).** CE already has much of this: `ce surfaces` (`surfaces/manifest.yaml` → `surfaces/render.py` → docker build-args + launch-env.sh), `cev3 onboard` greenfield/brownfield scaffold (`v3_installer.py`, `v3_greenfield.py`, `onboard_apply.py`), `ce launch` canonical seat launch (`launch_runtime.py`), the identity-registry.yaml SSOT concept, the containment backends, the signed install spec + wheels (`docs/llms-install.md`, `install.sh`). Read these. State precisely what is **reusable as-is**, what needs **templatizing/parameterizing**, and what is **genuinely net-new**. Cite file paths.
3. **Per-project ISOLATION model (the hard requirement: zero CE-vs-other-project mixing).** Cover: separate cloud VM (physical, chosen); separate GitHub org/repos; separate identities (per-project GitHub App install vs shared App, separate PATs, separate OpenBao instance/namespace); separate state root / brain / territory-map / SSOT; separate crons. Leverage CE's existing blast-radius isolation (containment + per-dev identity + small-blast-radius doctrine). Define what concretely GUARANTEES no cross-contamination and how a deployed fleet is prevented from ever touching CE-internal repos/creds.
4. **The IaC / one-click provisioning path.** Define the declarative artifact — a **"fleet manifest"** that extends/parallels `surfaces/manifest.yaml` + the identity-registry — and the provisioner. Choose the IaC tech (Terraform / cloud-init / Ansible / Nix / docker-compose) grounded in CURRENT (2026) practice AND what CE already uses (render.py→build-args is already IaC-adjacent). Specify the end-to-end flow: provision cloud VM → install the container/containment stack → render per-project fleet config from the manifest → bootstrap identities/secrets → launch seats → self-verify green. Include the **tier knob**.
5. **Irreducible human-gated bootstrap (be honest).** Governance + secret-zero mean some steps CANNOT be one-click: cloud-account auth, GitHub App install consent, OpenBao unseal / secret-zero, identity ratification. "One-click" = automate everything UP TO those irreducible consent/ratification acts and surface them crisply (mirror the R5 release-signing pattern). Enumerate the minimal human gestures per deployment.
6. **Tiering design.** What concretely differs between the lean Solo+CEO single-controller and the full multi-seat Fleet (seat count, OpenBao vs a simpler secret store, which crons, brain on/off, cost). One path, manifest-selected.
7. **Product framing.** How this doubles as the productizable "CE Autonomous Fleet" offering; relationship to existing strategy (deployment tiers Solo/Team/Autonomous-Fleet, agent-pointed-install model, the containerized-CE direction, OpenShell #82). What stays internal-only vs what's shippable.
8. **Phased build roadmap.** Bounded work-units, ordered, each with deliverable + existing-vs-net-new split; identify the long-poles.
9. **Risks.** Cost (N cloud VMs), secret-bootstrap complexity, GitHub-App multi-install/multi-tenant identity, and the self-referential **rented-surface-update** problem — each deployed fleet is itself a rented surface of CE that must be kept in sync with upstream CE improvements (tie to the `ce surfaces` mechanism + ce-ops#114 lesson).
