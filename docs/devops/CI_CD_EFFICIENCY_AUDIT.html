CE CI Efficiency Audit: Preserve Safety, Remove Fidelity Drift

Creator Engine's local and CI validation share substantial safety coverage, but their orchestration and PR-data inputs diverge. The practical sequence is to measure gates, consolidate shared definitions, and ratify any change that can weaken a safety property.

Timing limitation: trustworthy live CI timing telemetry was unavailable for this audit. The documented full-suite range (about 1–4 minutes) and check-examples range (about 60–90 seconds) are documentation, not measurements.

The current fidelity gap

Observed: local preflight can derive the work class and coupling exemption from carrier or local input, while CI evaluates the pull-request body snapshot in GITHUB_EVENT_PATH and a server-resolved comparison base. A carrier can therefore be locally coherent while the event-snapshot body is stale or otherwise different. Editing the live PR body and rerunning the same workflow event can still validate the old event-snapshot text; a new pull-request event supplies a new snapshot. Fetching the live body during validation would be a separate workflow proposal subject to the existing ratification and change-control contract.

Observed: local baseline comparison carries identical baseline/head failure IDs. Inference: this avoids blocking an author on an inherited failure, but the lack of freshness or identity constraints could normalize a long-lived failure. These are fidelity and safety design questions, not evidence that any present gate should be removed.

Ranked recommendations

Governance boundary: every recommendation below is a proposal. Any workflow, required-check, validator, or evidence-schema mutation remains subject to the existing ratification and change-control contract. A technical-risk assessment does not grant authority to mutate those surfaces.

1. Proposal: one machine-readable gate manifest

Technical-risk assessment: centralizing gate identifiers could reduce definition drift, while a parity test can preserve fail-closed behavior. Governance: design and implementation require the applicable ratification before changing workflow or validator behavior.

2. Proposal: one declared-work-class payload

First push: generate and locally validate the carrier-derived payload, and record that evidence without claiming comparison to a PR that does not yet exist. After PR creation: update the live PR body from the payload, then verify body/carrier parity locally and in CI after a new pull-request event supplies an updated body snapshot; rerunning an older event does not establish live-body parity. Governance: ratify the mechanism and failure contract before implementation, including any proposal to fetch the live body during validation.

3. Proposal: publish timing evidence

Technical-risk assessment: secret-safe per-gate duration, cache-status, test-count, and comparison-base artifacts would replace inference with observations and enable p50/p95 analysis. Governance: the artifact schema and workflow mutation still require the applicable review, ratification, and change control.

4. Proposal: investigate duplicate example sweeping

Technical-risk assessment: reuse an aggregate check-examples result only if measurements confirm overlap and malformed/well-formed negative coverage proves every present property remains covered. Governance: removal or consolidation of a check requires ratification.

5. Proposal: bound carried baseline failures

Subject to design ratification, replace unconstrained failure-ID parity with an explicit dated allowlist keyed to test node and base SHA. Expiry or node/SHA changes must fail closed.

6. Proposal: introduce path-aware local tiers

Subject to design ratification, always run carrier, class, confidentiality, and permissions checks locally; keep the full suite before merge and define escalation for validator/runtime surfaces. Seeded mutations must demonstrate no lost safety property.

7. Proposal: verify merge-group combined diffs

Subject to design ratification, add merge-group checks for manifest, sizing, and coupling—or prove pull-request-only sufficiency. A fixture with conflicting individually-green changes should be rejected.

Risks and open questions

  • Live Actions logs and timing data were not available to this read-only audit; instrument before claiming latency savings.
  • Tiering and baseline changes can weaken safety unless negative tests and ratification accompany them.
  • Current-main conclusions were anchored to the audited origin/main evidence; re-check the gate manifest as workflows evolve.
