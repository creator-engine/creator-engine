## 0. The three findings that reshape the decision

1. **OpenShell's egress is a per-endpoint choice, not a single posture — and it *supersedes* CE's open Q2 dichotomy.** Default network control is **L4** (deny-by-default; allow by destination host + port + *calling-binary identity* via `/proc/<pid>/exe` with trust-on-first-use hashing) with raw TCP passthrough and **no payload inspection**. **L7 inspection is opt-in per endpoint** via a `protocol: rest|websocket|graphql` field; the proxy auto-detects TLS and transparently terminates it with a **per-sandbox ephemeral CA** (injected into `NODE_EXTRA_CA_CERTS`/`REQUESTS_CA_BUNDLE`/`GIT_SSL_CAINFO`/etc.) to allow method/path matching and credential injection — but **even L7 sees only method/path, never request bodies**. So OpenShell ships *both* poles of CE's "advisory hostname allowlist vs. CA-terminating proxy" question as a per-endpoint knob, **plus** a binary-identity axis CE never had — but it does **not** solve exfiltration to an *allowed* host (NVIDIA's own docs concede "the agent can send workspace content, credentials, or conversation history to any reachable host"). *(NVIDIA OpenShell Security Best Practices + Policy Schema Reference, accessed 2026-06-02; Deconvolute Labs 2026-03-27; Dnotitia Part 3 2026-04-23.)*

2. **The durable, well-backed thing is the *pattern* (out-of-process enforcement), not OpenShell-the-product.** OpenShell is genuinely **v0.0.53, Apache-2.0, "Alpha software — single-player mode," multi-tenant on the roadmap with no date, ships "AS IS."** Yet the same pattern is converging across the industry — Anthropic's `sandbox-runtime` (Oct 2025), Microsoft's Agent Governance Toolkit (2026-04-02), the vendor-neutral **Agent Control Standard (ACS, ~2026-05-27)** — and Anthropic's own May-2026 post-mortem independently proves *why* it's right. **CE's existing mandate (keep the runner behind an abstraction; OpenShell = first backend, not the architecture) is exactly correct and is *strengthened*, not changed, by this research.** *(Futurum 2026-06-01; BusinessWire/ACS 2026-05-27; Anthropic Engineering 2026-05-25.)*

3. **Anthropic's published red-team is the strongest external validation of CE's whole security thesis — and a precise warning.** Across Anthropic's products the **battle-tested kernel primitives (gVisor, seccomp, hypervisors) held against well-resourced adversaries, while their *own custom allowlist proxy was the weakest, failing layer*** — a red-team had Claude exfiltrate `~/.aws/credentials` **24 of 25 times through an *authorized* egress path**. Lesson, in Anthropic's words: *"Design for containment at the environment layer first, then steer behavior at the model layer."* For CE plane C this means: **the kernel/container boundary is trustworthy; the egress *policy* layer is the risk locus; and the sandbox must never be the sole boundary.** *(Anthropic Engineering "How we contain Claude across products," 2026-05-25; Simon Willison 2026-05-30; The Agent Report 2026-05-28.)*

## 1. OpenShell — precise current technical profile (from the public record)

**Identity / license / maturity.** `github.com/NVIDIA/OpenShell`, "the safe, private runtime for autonomous AI agents." **Apache-2.0**, written ~89% Rust, ~6.6k stars. **v0.0.53 released 2026-06-01**; ~1 tagged release/day cadence (v0.0.49 2026-05-26 → v0.0.53). Self-labeled **"Alpha software — single-player mode … one developer, one environment, one gateway,"** ships **"AS IS, without warranty,"** Kubernetes path "Experimental … breaking changes," GPU passthrough "Experimental." Multi-tenant is **roadmap-only, no published date.** Zero published GitHub security advisories; SECURITY.md routes to NVIDIA PSIRT. *(OpenShell README/releases/Security tab, 2026-06-01/02.)*

**Architecture.** Control-plane/data-plane split:
- **Gateway** — control-plane API; sandbox lifecycle + auth boundary; owns durable state (sandboxes, policies, providers, inference config) via a Store (SQLite/Postgres) over gRPC.
- **Sandbox** — isolated container; a **Supervisor** drops privileges and applies kernel isolation in a `pre_exec` phase before the agent starts; sandboxes connect *outbound* to the Gateway.
- **Policy Engine** — **OPA/Rego** (the `regorus` crate) evaluates each decision.
- **Privacy Router** — privacy-aware LLM routing; intercepts `https://inference.local`, **strips caller credentials, injects backend credentials**, routes to a policy-chosen backend (can keep sensitive context on local compute).
- **Egress proxy** — a transparent/CONNECT proxy in the sandbox's own network namespace (veth to a host-side proxy IP); all outbound traffic is forced through it.
- **Gateway packaging** — a local/all-in-one mode runs an **embedded K3s inside a single `--privileged` Docker container** (`openshell/cluster` image); a non-privileged gateway-container (Docker-socket driver) and a Helm/K8s StatefulSet are alternatives. **NVIDIA is actively migrating the gateway off `--privileged` into a microVM (Discussion #558, adopted 2026-05-09) "to remove a meaningful class of risk"** — i.e., the architecture is still in flux. *(DeepWiki; GitHub issues #415/#878/#558; Spheron 2026-04-03.)*

**The four policy domains and how each is enforced (OS-level).**
| Domain | Mechanism | Lifecycle |
|---|---|---|
| **Filesystem** | **Landlock LSM** (kernel), applied pre-exec; system paths ro by default, `/sandbox`+`/tmp` rw; `..` blocked; ≤256 paths | **Static — locked at creation** |
| **Process** | **seccomp BPF** syscall filtering + privilege drop (non-root; root rejected); blocks `ptrace`, `bpf`, `mount`, `setns`, `unshare(CLONE_NEWUSER)`, `memfd_create`, `io_uring_setup`, `process_vm_readv/writev`, `userfaultfd`, `perf_event_open`, etc.; runs in a dedicated netns | **Static — locked at creation** |
| **Network/egress** | CONNECT/transparent proxy + OPA; L4 (host+port+binary) default, opt-in L7 (method/path) with TLS termination via per-sandbox ephemeral CA | **Dynamic — hot-reloadable** |
| **Inference** | Privacy Router at `inference.local`; allowed backends provider-configured | **Dynamic — hot-reloadable** |

The **static/dynamic split** is the core of the model: filesystem + process are kernel-frozen at creation (changing them requires destroy+recreate); network + inference can be hot-reloaded for the agentic-approval loop. *(NVIDIA Policy Schema Reference + Security Best Practices, 2026-06-02; DeepWiki.)*

**Egress mechanism (the load-bearing fact, fully verified).** See §0.1. The single corrected nuance vs. the Brief's "hostname-level" assumption: **default = L4 host+port+binary passthrough (no inspection); L7 method/path rule evaluation is opt-in; TLS termination is automatic for L7 but bodies are never inspected.** A broad allowlist entry (e.g. `github.com`) at L4 is therefore a documented exfiltration channel.

**Credential model.** Two layers: (a) named **providers** (credential bundles) injected as **env vars at runtime, never written to the sandbox filesystem**; (b) for proxy-routed HTTP, the proxy substitutes an **opaque placeholder token** (`openshell:resolve:env:NAME`) in the agent's environment and resolves it to the real value only at the proxy boundary (headers/path/query — **not bodies**; **not** TLS-passthrough endpoints), failing closed (HTTP 500) on an unresolvable placeholder. The **Privacy Router** keeps inference-provider keys entirely outside the sandbox. *(OpenShell Providers + inference.local docs; Dnotitia 2026-04-23; vietanh.dev 2026-03-17.)*

**Platforms / drivers / hardware.** Hosts: **macOS, Windows-with-WSL2, Linux.** Compute drivers: **Docker, Podman, MicroVM (KVM/QEMU/Hypervisor.framework), Kubernetes.** **NVIDIA GPU hardware is NOT required** for non-GPU agent use (decoupled in v0.0.50; base image ships without GPU drivers; GPU is experimental/opt-in). Supported agents: **Claude Code (full), Copilot CLI (full), OpenCode (partial), Codex (no default policy — custom required), OpenClaw (via NemoClaw), Ollama, Pi** — design goal is "run unmodified." *(README + NVIDIA Technical Blog 2026-03-16.)*

**Windows-AI-PC integration (verified, with a correction).** The **"NVIDIA and Microsoft Reinvent Windows PCs for the Age of Personal AI"** announcement is real and dated **2026-05-31** (NVIDIA Newsroom + Microsoft Windows Experience Blog; wire 2026-06-01; GTC Taipei). It pairs *"new Windows security primitives and the NVIDIA OpenShell runtime."* **Correction to the starting facts:** OpenShell itself is **Linux/container-based** and runs on Windows **via WSL 2**; it does **not** build on Windows OS primitives *today*. The native-primitive coupling ("OpenShell is *coming* to Windows, built on Microsoft's new security primitives") is **forward-looking, tied to fall/Q4-2026 hardware** (RTX Spark laptops/desktops "this fall" from ASUS/Dell/HP/Lenovo/Surface/MSI, +Acer/GIGABYTE; DGX Station for Windows Q4). The Windows OS primitives are framed as **identity, containment, manageability** (note: "manageability," not "policy"). **Only Hermes Agent (Nous Research) and OpenClaw are named as committed Windows-app integrators of OpenShell+primitives — Claude Code/Codex/Copilot are *supported-to-run-unmodified*, not launch partners.** *(NVIDIA Newsroom + Windows Experience Blog 2026-05-31; shashi.co 2026-06-01.)*

**Enterprise backing.** Launched at GTC 2026 (2026-03-16) within the **NVIDIA Agent Toolkit** framing with ~17 adopters (Adobe, Salesforce, SAP, ServiceNow, Siemens, CrowdStrike, Cohesity, Cadence, Dassault, Canonical/Ubuntu, Red Hat AI…). **ServiceNow "Project Arc"** runs every agent action inside OpenShell ("early preview"; ServiceNow is "building on and contributing to OpenShell"). Cohesity is at intent stage. These are **previews/intent, not GA.** *(NVIDIA Newsroom 2026-05-31; ServiceNow Newsroom 2026-05-05.)*

## 2. Security-assurance assessment (defensive)

**The "policies out of the agent's reach / can't leak creds even if compromised" property — how well-founded?**

- **The design rationale is independently well-founded.** The published literature is clear that **in-process / application-layer guardrails are insufficient for autonomous agents** — an LLM structurally follows injected instructions and a guardrail model is itself injectable (Simon Willison's "lethal trifecta," 2025; OWASP LLM Prompt-Injection Prevention Cheat Sheet; Cisco "guardrails aren't enough," 2026). Moving the control point **outside and below the agent** is therefore a sound defensive principle — and it is **CE's own locked security-boundary principle** (Brief §3). OpenShell's Landlock + seccomp + netns + OPA-proxy implementation is genuinely kernel/out-of-process, and independent reviewers rate this the strongest aspect ("policy-as-physics," htek.dev 2026-03-23; Node9 review 2026-03-30).

- **The *absolute* "even if compromised" claim is overstated and contested — treat as residual-risk-bearing.** The verified, defensible statement is narrower:
 - **Provider/inference credentials are genuinely protected** (placeholder + Privacy Router; the agent never holds the raw value of proxy-routed creds). ✓
 - **But any secret/data *usable inside the sandbox* (tool env-var creds, workspace content, conversation history) remains exfiltratable over *allowed* egress** — NVIDIA's own best-practices doc concedes this verbatim, and independents corroborate (Lasso Security 2026-04-23: within-allowed-egress exfil with *no policy violation* — "cannot evaluate intent"; Cisco 2026-03-16: infra controls alone insufficient against exfil over allowed channels). The Red Hat "even a compromised agent holds nothing to exfiltrate" (2026-05-20) is accurate *only* for the proxy/inference path.
 - **The boundary can silently degrade:** on kernels without Landlock (pre-5.13), or with `compatibility: best_effort`, the filesystem layer runs **without kernel restrictions** ("the agent can access any file the process user can access") — a degradation mode, not fail-closed (vendor-documented).
 - **The documented trust boundary is "governs *what* an agent can reach, not *how* it uses approved resources"** — the **"logical governance gap"** (it won't stop an authorized agent running `DROP TABLE users`). This is the most consistent independent critique (Node9, Cisco) — both conflicted (they sell the complementary layer), **but they agree the gap exists**, and NVIDIA's own docs describe it.

- **Maturity / verification posture.** **No disinterested third-party security audit, red-team report, or CVE for OpenShell was found** in the public record as of 2026-06-02. Most "independent" coverage is complementary-vendor co-marketing (Cisco, Node9, MindStudio) or favorable infra-blogs. **Disambiguation:** the headline **CVE-2026-25253** (1-click RCE, CVSS 8.8) belongs to **OpenClaw**, a *different* product (fixed 2026.1.29) — frequently conflated with OpenShell; it is **not** an OpenShell vulnerability. (One verifier agent floated "OpenShell CVE-2026-44113/44115"; the dimension that specifically searched the GitHub Security tab + NVD found **zero** OpenShell advisories, and I could not corroborate those numbers — treated as a verifier artifact and the authoritative finding is **zero published OpenShell CVEs**.)

**Confidence:** HIGH that the architecture is sound and a real improvement over in-process controls; HIGH that the absolute "even if compromised" guarantee is overstated and config-dependent; HIGH that no independent adversarial validation exists yet. **What remains unverified (no technique pursued):** the boundary's strength under adversarial/at-scale conditions, the transitive risk of K3s-in-a-`--privileged`-container, and multi-tenant cross-isolation.

## 3. Egress decision (Q2)

**If CE adopts OpenShell as a plane-C backend, the egress posture is decided *by* OpenShell, per-endpoint, and the Brief's advisory-vs-CA-terminating dichotomy is mooted.** Concretely:

- **Deny-by-default is the floor** ("every sandbox starts with minimal outbound access; every connection must be explicitly allowed").
- **Per-endpoint, the policy author chooses the assurance level** — L4 (host+port+**binary**) when tools must "just work," or L7 (TLS-terminated method/path) when an endpoint warrants content-level allow/deny + credential placeholder injection. This is **strictly more expressive** than CE's planned binary choice, and the **calling-binary axis** (`/proc/<pid>/exe`) is a capability CE's `worker-container-policy` egress schema lacks.
- **The residual that does *not* go away:** OpenShell inspects **no request bodies** even at L7, so a broadly-allowed host remains an exfil channel. This is the *same* residual CE already understood — now vendor-confirmed.

**Therefore Q2's refined answer (whether or not OpenShell is adopted):**
1. **Egress posture = deny-by-default, enforced *outside the agent*, with per-endpoint L4/L7 selection** — adopt this contract regardless of backend.
2. **Default to L4 host+port(+binary) allowlist; reserve L7 TLS-termination for the few high-value endpoints** (e.g. the model API, the package registry, `api.github.com`) where method/path scoping + credential injection earns its keep and the cert-pinning breakage (documented friction: NemoClaw issue #307; Anthropic's `srt` hits the same cert-trust requirement) is acceptable.
3. **Keep an always-on backstop** — a hash-chained, signable side-effect/egress log + a pre-push secret scan + least-privilege short-lived tokens — because *no* network layer here stops body-level exfil to an allowed host. This is exactly Anthropic's "sandbox is necessary, not sufficient" lesson.
4. **CE's current in-repo egress posture is a *stub*, so any adoption is a net gain.** `worker_runtime.py`'s `PodmanCommandRunner.egress_primitive()` returns `None`, meaning the live CLI **refuses any non-empty egress allowlist** (`EgressNotEnforceable`) because *no enforcement primitive is implemented*. CE has correct *intent* (refuse-if-unproven) but **no working egress boundary today.** OpenShell — or `srt`, or Pipelock — would supply the missing primitive.

## 4. Enforcer + Q4 — does OpenShell subsume the planned in-container enforcer?

**Substantially yes, and it largely dissolves the build — but not the abstraction.** Mapped against the prior v3-spec Architect's plane-C enforcer (the "genuinely-ours" differentiator) and the in-repo seeds:

| CE planned enforcer layer | OpenShell equivalent | Verdict |
|---|---|---|
| Hardened ephemeral container (cap-drop, ro-rootfs, seccomp, no host mounts, non-root) | Sandbox + Supervisor (seccomp BPF, privilege drop, Landlock, netns, locked-at-creation) | **Subsumed** (and more rigorous than CE would hand-roll) |
| Deny-by-default egress proxy (the primary anti-exfil control) | CONNECT/OPA proxy, L4/L7, binary-scoped | **Subsumed + superset** |
| Credential broker passing secret *names* not *values* | Providers (env injection) + placeholder/proxy resolution + Privacy Router | **Subsumed + superset** (placeholder model is stronger than CE's name-passing) |
| Forbidden-mount refusal (`worker_container_policy`) | Default-deny mount manifest (Landlock); paths locked at creation | **Subsumed** |
| Side-effect / egress audit log | L4/L7 deny logging | **Partial** — OpenShell logs reachability; CE still wants its hash-chained, signable evidence spine |
| Command/secret *advisory* classifier policy (`hook_check`) | Not provided (this is the "logical governance gap") | **Keep — CE-owned** |

**So the enforcer-extraction question (the prior architect's open trigger) largely *dissolves* in the OpenShell-adopted world:** you don't build the kernel-isolation enforcer at all — you **drive OpenShell's Gateway API.** What CE keeps building is thin:
1. A **runner/enforcer adapter** that provisions an OpenShell sandbox + emits the right policy YAML (and can fall back to a CE-orchestrated gVisor container + Pipelock-style proxy where OpenShell is unavailable/immature).
2. The **advisory classifier layer** (`is_secret_path` / `classify_mechanics`) as the **logical-governance / audit overlay** OpenShell explicitly does *not* provide — this is now *more* clearly justified, not less: it occupies the documented gap (Node9/Cisco). Note that in this model the old "deny `gh pr merge` / `git push` without authority" largely evaporates anyway — the scoped GitHub-App token can't merge (ruleset), and egress is policy-bound.
3. The **hash-chained side-effect/evidence spine** (completion-report/evidence schemas survive per Brief §7) layered on OpenShell's logs.

**Reconcile with the seeds (`worker_runtime.py`, `worker_container_policy.py`, `schemas/worker-container-policy.schema.yaml`):** **adopt-and-drop the runtime, keep-and-map the policy schema.** The rootless-Podman lifecycle in `worker_runtime.py` is **superseded** by OpenShell's Gateway (and its claim/lease binding — `_require_live_claim`/`_require_live_lease` — is the v2 deadlock vector, already slated for deletion). But `worker-container-policy.schema.yaml` is a **near-isomorphic precursor to OpenShell policy** (role, image digest-pin, default-deny mount manifest, egress host/port/protocol rules, secret-name allowlist, forbidden-mount predicate) — it should become the **CE-side declarative policy that the adapter *translates* into OpenShell YAML** (and into a gVisor+proxy config for the fallback backend). That preserves CE's validator-dogfooding (the mount/forbidden predicates → a `ce_runtime_policy` check) while renting the *enforcement*.

**Q4 (production plane-C):** The prior decision — "plain CE-orchestrated hardened container, with self-hosted-runner behind a runner abstraction" — **holds and is refined**: production plane-C = **a CE-orchestrated isolation backend behind the runner abstraction, with two first-class implementations: (a) a hardened gVisor container + capability-separation egress proxy (ships now, no alpha dependency, no KVM needed), and (b) an OpenShell sandbox (adopt as it matures, aligned to the fall rollout).** Hosted GitHub Actions remains the plane-A/B CI substrate only (its 6h cap + no-GA-egress-firewall + no-interactive-shell rule it out for the long-lived plane-C agent, per the prior architect).

## 5. Platform-wide implications (where OpenShell touches every aspect of CE v3)

- **Agent-native install (P1).** OpenShell deepens, not replaces, CE's install contract. `ce-install` gains a step: *provision/verify a plane-C runtime backend* — for the OpenShell backend, "deploy/point-at an OpenShell Gateway + push the policy bundle." This **fits CE's "agent reads a declarative install contract" model** (OpenShell is itself declarative-YAML + single-binary installer). Keep the **locked guardrail**: the human creates the GitHub-App key and ratifies the plan before apply; the OpenShell provider/credential setup is part of that ratified plan. *Net: one new idempotent install step behind the runner adapter.*
- **Harness model.** **Simplifies.** OpenShell runs **Claude Code unmodified** (full default-policy coverage); Codex/OpenClaw also run (Codex needs a custom policy). CE's harness-seat handling collapses toward "pick a supported agent, hand it a sandbox" — the bespoke `.claude/hooks` posture machinery (already slated for deletion) is even less needed.
- **Credential / token handling.** **Layered, not replaced.** The GitHub-App scoped-token model (1h, repo+permission-scoped) stays — it's the *forge* credential. OpenShell's provider/placeholder/Privacy-Router model governs *how that token and any model keys live inside the sandbox* (env injection, never on disk, placeholder for proxy-routed use). The two compose cleanly: orchestrator mints the 1h token → injects it as an OpenShell provider → the agent uses it; OpenShell ensures it never lands on the sandbox FS and (optionally, at an L7 endpoint) the agent never reads its raw value.
- **Orchestrator.** **Stays thin; thins further.** The orchestrator drives OpenShell's **Gateway API** (create sandbox, set policy, attach providers, collect results) instead of bespoke `podman run`. This corroborates the prior architect's "orchestrator is thin (glue); the enforcer is the thick part" read — and now even the enforcer is *rented*, so CE's authored surface shrinks to: mint token → gate on approved plan → provision sandbox via adapter → collect evidence → teardown. (This further weakens the Brief §4 "orchestrator is thick" market assumption, consistent with the prior report's pushback.)
- **Audit / evidence spine.** **Integrate, don't duplicate.** OpenShell's L4/L7 deny logs feed CE's hash-chained side-effect log + completion-report/evidence schemas. CE keeps its **signable, tamper-evident** spine (OpenShell's logging is not pitched as cryptographically chained); OpenShell is a *source*, not the system of record. (Git/PR history remains the plane-A audit spine.)
- **Operating-mode / autonomy substrate, forge-adapter, runner abstraction, ratification gate.** **Orthogonal and intact.** OpenShell governs runtime *containment*; CE's operating-mode policy governs *per-action autonomy*; the forge-adapter governs *coordination*; the ratification gate (approved issue/plan-PR before the sandbox starts) is unchanged — it simply now gates `adapter.provision(openshell_sandbox)`.
- **Product positioning / GTM.** **Adopt the message and the pattern now; adopt the runtime as it matures.** OpenShell normalizes CE's hardest-to-explain thesis — *"the agent is dangerous; enforce out-of-process"* — for the exact trust-sensitive, no-devops market CE targets, and the **fall RTX-Spark Windows rollout is a real narrative/distribution window.** Position CE as **"agent-native and OpenShell-ready"**: ship the MVP on the portable container+proxy backend, and have the OpenShell backend land *as* the fall hardware arrives. **Do not gate MVP timing on OpenShell GA** (it's alpha/single-player with no multi-tenant date — which directly bites the 6–10-person team target if they share one gateway; CE's single-Controller-per-container maps cleanly to "single-player," so per-Controller sandboxes are the safe pattern).
- **MVP gate map / sequencing.** **Unchanged in structure.** The prior G-i/G-ii/G-iii kickoff (advisory author-time hook → promote `path_manifest_fidelity` to the PR-diff gate → GitHub-native coordination config) and G-1/G-2/G-3 MVP are **untouched** — OpenShell only changes *what the runner adapter provisions* in G-1. Add one pre-committed item: **G-1 ships the gVisor+proxy backend; an OpenShell backend is a fast-follow spike behind the same adapter.**

**Adopt-vs-build conclusion (corroborated, HIGH confidence):** **Don't build a custom sandbox.** The realistic build is the **thin runner abstraction/adapter**; the isolation primitive is *adopted*. Two composable layers behind that adapter: **(1) isolation = gVisor (default, no-KVM) / Kata-Firecracker (where KVM) / OpenShell (as it matures) / managed (optional);** **(2) egress+secrets = a capability-separation proxy (Pipelock/agent-vault) or OpenShell's built-in proxy.** This is precisely OD-04's "runner stays behind an abstraction" property.

## 7. Coupling, maturity, risk, and a phased adoption recommendation timed to the rollout

**Coupling / forkability hedge — real but *weaker* than assumed.** OpenShell's Apache-2.0 Linux/container core is genuinely forkable and runs without NVIDIA GPUs (this part of the thesis holds). **But its strongest *Windows* enforcement depends on proprietary Microsoft OS primitives + the OEM distribution channel — neither forkable.** So the hedge must be: **depend on the portable out-of-process-enforcement *contract* via the runner abstraction, not on the Windows-primitive-coupled distribution.** *(shashi.co 2026-06-01.)*

**Vendor-stability bet — partially supported; reframe it.** NVIDIA is dramatically more financially robust (recent fiscal-year revenue on the order of hundreds of billions, growing fast) — a strong platform bet. **But framing Anthropic as a "smaller, not-yet-profitable vendor" understates it:** Anthropic is at a very large annualized run-rate, recently raised a multi-billion-dollar round at a high valuation, with reported much-larger talks and a near-term breakeven target. More importantly: **adopting OpenShell does NOT remove the Anthropic dependency** — CE's agent *is* Claude/Claude Code. This is a **two-vendor bet (runtime on NVIDIA/MS, model on Anthropic), not a substitution.** OpenShell's genuine de-risking is making the *runtime layer* rentable + forkable — which the runner abstraction already secures regardless of which backend wins. *(NVIDIA/SEC filings 2026-05-20; Anthropic funding 2026-02-12; VentureBeat 2026-05.)*

**Does the timing window pull adoption earlier? Yes — for engagement and messaging; no — for production reliance.** The fall rollout + multi-vendor standardization make OpenShell **far more backed than a "v0.0.53 alpha" label implies**, which justifies **prototyping against its Gateway API and policy model *now*** and shipping an OpenShell backend aligned to the fall hardware. It does **not** justify making an alpha, single-player, unaudited, AS-IS runtime the *foundation* of the MVP.

**Recommended phasing (timed to the rollout):**
- **Now (MVP):** Ship plane C on the **portable contract** — a hardened **gVisor** container + a **capability-separation egress proxy** (Pipelock/agent-vault or a thin CE proxy) + force-off self-service escape + CE's classifier/audit overlay — **behind the runner abstraction.** This satisfies the out-of-process-enforcement standard today with zero alpha dependency, and mirrors Anthropic's bubblewrap→gVisor→VM ladder.
- **Summer–fall 2026 (pilot, fast-follow):** Build the **OpenShell backend** behind the same adapter; pilot it in the single-Controller-per-sandbox (= "single-player") configuration that matches OpenShell's current maturity. Translate `worker-container-policy` → OpenShell policy YAML. Adopt the **"agent-native, OpenShell-ready"** GTM message.
- **Post-multi-tenant-GA (revisit):** When OpenShell ships multi-tenant + an independent security validation exists, re-evaluate promoting it to the *default* backend. Until then it's a peer of gVisor behind the abstraction.

## 8. Net recommendation, confidence, reversal triggers, and thin evidence

### 8.1 Net recommendation
**Adopt the *pattern* and the *message* now; adopt OpenShell as a *first-class backend behind the runner abstraction*, on a fast-follow timeline aligned to the fall Windows-AI-PC rollout — never as the MVP foundation.** Concretely:
1. **Q2 resolved:** egress = **deny-by-default, enforced outside the agent, per-endpoint L4/L7**, with always-on backstops (signed side-effect log, secret scan, short-lived scoped tokens). OpenShell's model *supersedes* the advisory-vs-CA-terminating dichotomy; CE adopts the same per-endpoint contract regardless of backend. **Fix the in-repo egress stub** — CE has no working egress boundary today.
2. **Enforcer/Q4 resolved:** **stop planning to build a kernel-isolation enforcer.** Ship a **gVisor + capability-separation-proxy** backend now; add an **OpenShell** backend next; keep **only** the thin runner adapter, the **advisory classifier/logical-governance overlay** (the documented gap OpenShell leaves), and the **hash-chained evidence spine**. Adopt-and-drop `worker_runtime.py`; **keep-and-translate** `worker-container-policy.schema.yaml` as CE-side policy. The enforcer-extraction trigger **dissolves** (you're renting the enforcer).
3. **Architecture/GTM:** OD-04′ is reinforced — *runner stays behind an abstraction; the standard is the out-of-process-enforcement pattern; OpenShell is the first runtime backend, not the architecture.*

### 8.2 Confidence
- OpenShell technical profile & egress mechanism: **HIGH** (vendor docs + 2 independent analyses + primary fetches, adversarially tightened).
- "Pattern is the standard; don't couple MVP to the alpha": **HIGH** (multi-vendor convergence + alpha self-labeling).
- "Sandbox necessary-not-sufficient; proxy/policy is the risk locus": **HIGH** (Anthropic's own published red-team).
- "OpenShell subsumes most of the planned enforcer": **MEDIUM-HIGH** (clear feature mapping; gVisor-as-OpenShell-driver and exact adapter fit unverified).
- Vendor-stability / GTM timing: **MEDIUM** (strategic inference over solid financial/announcement facts).

### 8.3 Decision-reversal triggers
- OpenShell ships **multi-tenant GA + an independent security audit** → promote it from peer-backend toward default backend.
- An **independent red-team / CVE** materially weakens OpenShell's kernel-isolation claims (or the K3s-`--privileged` packaging) before the microVM-gateway migration lands → keep it firmly behind the abstraction; do not message "OpenShell-secured" without caveat.
- The **fall Windows-primitive substrate slips or ships without durable Microsoft support commitments** → the GTM timing thesis weakens; lead with the portable gVisor backend.
- **gVisor turns out *not* to be an OpenShell compute driver** and CE wants the no-KVM path *with* OpenShell → the "one backend covers both" simplification breaks; keep gVisor+proxy as an independent backend.
- **GitHub ships a GA L7 egress firewall for hosted Actions** sooner than expected → re-evaluate whether a hosted runner can host plane C (currently ruled out).

### 8.4 Where my evidence was thin (honest caveats)
- **No disinterested third-party security audit / red-team / CVE exists for OpenShell** — the strongest "even if compromised" claims rest on NVIDIA/partner sources; the sharpest critiques are conflicted competitors (Node9, Cisco). The boundary's adversarial strength is **architecturally argued, not empirically proven**.
- **No published multi-tenant GA date** — the single-player→multi-tenant gap (load-bearing for the 6–10-person target) is undated.
- **Gateway topology is in flux** — embedded-K3s-in-`--privileged`-Docker is one (transitional) mode; the microVM-gateway migration (Discussion #558) is in-flight; several canonical NVIDIA doc URLs 404'd, so some topology facts lean on DeepWiki + GitHub issues + search synthesis rather than a single rendered page.

- **5 of 28 verifier agents failed structured output**; each claim retains ≥2 verdicts and adjacent coverage, but one verifier conflated OpenShell with Docker Sandboxes (corroborating the *industry pattern* of placeholder+proxy creds — useful — but not OpenShell-specific), and another floated unconfirmed OpenShell CVE numbers explicitly down-weighted.
