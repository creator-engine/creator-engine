## 2. Executive Decision

Build CE's secret and identity plane behind a CE-owned
`SecretIdentityBackend` adapter. The default implementation is OpenBao,
self-hosted by the controller/operator infrastructure. CE seats and worker
containers never receive OpenBao admin tokens and should not authenticate to
OpenBao directly in the first production cut. They request logical secret refs
from CE's broker/orchestrator, and the broker returns only value-free grant
metadata to CE records.

OpenBao is a good fit because it provides secure key/value storage, dynamic
secret issuance, leasing, renewal, revocation, identity-based access, and an
open-source governance posture. Current release state as of 2026-06-19:
OpenBao v2.5.5 was released on 2026-06-17 with security and bug fixes. The API
surface is Vault-compatible by intent, but OpenBao's own HTTP API docs still
warn that backwards compatibility is not yet promised even under the `/v1`
prefix. CE should therefore bind to a small adapter surface and test against a
pinned OpenBao minor release, not scatter raw Vault calls across the codebase.

OpenBao's HTTP API uses `/v1` routes, requires TLS in normal deployments, and
accepts tokens via `X-Vault-Token` or `Authorization: Bearer`. Existing Vault
client libraries should mostly work with OpenBao, but CE should initially use a
minimal internal HTTP client or subprocess wrapper behind the adapter so the
behavior is testable offline and replaceable by HashiCorp Vault/HCP later.

## 3. Non-Negotiable CE Invariants

1. **Broker-only access.** Agent seats do not hold OpenBao admin/root tokens,
   unseal keys, App PEMs, or provider admin credentials.
2. **Secret values never enter CE evidence.** Values do not appear in argv,
   tmux panes, dispatch records, runtime evidence, side-effect ledgers,
   path manifests, changelog fragments, issue comments, or PR bodies.
3. **Names and refs are allowed.** CE records may contain logical
   `SecretRef`, `grant_id`, lease/accessor references, policy digest,
   expiry, and audit correlation metadata.
4. **Audit-before-issue.** The backend refuses issuance/materialization when
   OpenBao audit devices are not enabled or cannot accept writes. OpenBao's own
   docs state that audit devices log API request/response interactions and
   that requests can be blocked when audit devices cannot write.
5. **Short lived by default.** Per-run credentials use TTLs bounded by the CE
   claim/runtime-policy TTL and never longer than the upstream ceiling for the
   credential class. GitHub App installation tokens keep the existing <= 1h
   ceiling in `mint_scoped_token`.
6. **Fail closed offline.** If OpenBao is unreachable and no ratified migration
   fallback is enabled, the run refuses before provisioning or secret
   materialization.
7. **No direct worker fallback to host files.** `~/.ce-keys`, `~/.hermes/.env`,
   PEM files, and bootstrap tokens become migration sources only. They are not
   a steady-state runtime source after cutover.
8. **Controller/root split.** OpenBao root/unseal and break-glass authority
   stay operator-controlled. The controller/broker gets narrow auth roles.

## 4. CE-Side Adapter Interface

The adapter should be a pure interface first, mirroring the local
`RunnerBackend` style: frozen value objects, no import-time I/O, explicit
errors, and a registry keyed by backend name. The OpenBao implementation is a
later gate behind this interface.

```python
from __future__ import annotations

from dataclasses import dataclass
from typing import Mapping, Protocol, Sequence


@dataclass(frozen=True)
class SecretRef:
    backend: str                  # "openbao" | "vault" | "local-fake"
    mount: str                    # e.g. "ce-kv"
    path: str                     # logical path, no value
    field: str                    # key within the secret document
    version: int | None
    purpose: str                  # "github-app-pem", "model-key", ...
    owner_ref: str                # CE identity/seat/ref, opaque
    policy_sha: str               # 64-hex policy binding


@dataclass(frozen=True)
class SecretRequest:
    run_id: str
    seat_id: str
    repo: str
    secret_ref: SecretRef
    ttl_seconds: int
    delivery: str                 # "file" | "env" | "socket" | "none"
    requested_capabilities: tuple[str, ...]
    audit_context: Mapping[str, str]


@dataclass(frozen=True)
class SecretGrant:
    grant_id: str
    run_id: str
    seat_id: str
    secret_ref: SecretRef
    lease_id: str | None
    token_accessor_ref: str | None
    issued_at: str
    expires_at: str
    delivery_ref: str | None      # path/socket/env-name ref, never value
    audit_ref: str


@dataclass(frozen=True)
class IdentityDescriptor:
    identity_ref: str
    seat_id: str
    human_id: str | None
    github_login_ref: str | None
    email_ref: str | None
    reviewer_persona_ref: str | None
    policy_refs: tuple[str, ...]


class SecretIdentityBackend(Protocol):
    backend_key: str

    def validate_config(self) -> None:
        """Refuse before side effects when backend config or audit is unsafe."""

    def resolve_identity(self, seat_id: str) -> IdentityDescriptor:
        """Return value-free identity metadata for a CE seat."""

    def issue(self, request: SecretRequest) -> SecretGrant:
        """Authorize and create a value-free grant; secret value is not returned."""

    def materialize(self, grant: SecretGrant, target_ref: str) -> SecretGrant:
        """Expose the value to a narrow target and return updated value-free metadata."""

    def revoke(self, grant: SecretGrant) -> SecretGrant:
        """Revoke/expire the grant and return value-free revocation metadata."""

    def collect_audit(self, grant: SecretGrant) -> Mapping[str, str]:
        """Return audit correlation metadata only, never request/response values."""
```

### Interface Rules

- `issue()` validates `SecretRequest` against CE runtime policy before contacting
  OpenBao. Invalid repo, TTL, policy SHA, unlisted secret, or forbidden
  controller-key class refuses before I/O.
- `issue()` returns only `SecretGrant`. The live value is not part of the public
  port type.
- `materialize()` is the only method that crosses a value into a runtime target.
  It writes to a tmpfs file, env injection seam, or socket owned by the runner
  backend. It does not return the value to the orchestrator.
- `collect_audit()` returns correlation only: grant id, backend mount/path,
  OpenBao token accessor reference or lease id where available, audit device
  state hash, and CE run id.
- A fake backend must exist for tests. It proves policy/ref flow without storing
  values or running OpenBao.
- An OpenBao backend module must import no validator checks and do no I/O on
  import.

### Fit With Existing CE Seams

- `RunnerBackend` still owns provision/run/collect/teardown.
- `SecretIdentityBackend` becomes the host-side credential broker behind the
  existing `TokenMinter` and worker secret grant seams.
- GitHub App minting should reuse the current `mint_scoped_token` contract:
  OpenBao stores the App private key; the CE composition root reads it inside
  the broker, mints a JWT/installation token, maps the result to value-free
  `MintedCredential`, and revokes it through the existing revoke seam.
- For static provider keys, the broker uses OpenBao KV v2 and materializes the
  key only to the target runtime channel. The evidence contains only
  `secret_ref`, `grant_id`, `expires_at`, and audit correlation.
- For future dynamic engines, the backend records the OpenBao `lease_id` and
  revokes it on teardown.

## 5. OpenBao Deployment Shape

### Runtime Placement

OpenBao should run outside worker/agent containers as a controller-owned fleet
service. The controller decides the host. The first production shape should be:

- one self-hosted OpenBao service for the CE fleet;
- TLS-only listener;
- integrated storage suitable for a small initial cluster, with HA/raft
  hardening deferred to deployment planning;
- no direct public exposure;
- controller/broker network access only;
- operator-controlled root/unseal and break-glass path;
- server-managed audit devices enabled before any CE secret import.

OpenBao install methods include native packages, container registry,
precompiled binaries, source builds, and Helm. Because the host is TBD, this
design does not choose package-vs-container. The implementation should make the
server URL, CA bundle, namespace/mount names, and auth method config explicit
deployment settings.

### Auth Methods

Recommended auth posture:

1. **Controller/broker machine identity, Phase 1:** AppRole. OpenBao documents
   AppRole as oriented to automated workflows, machines, and services. The
   controller gets a narrow role, short TTL, explicit max TTL, and a policy
   limited to the paths needed for CE brokering. AppRole RoleID/SecretID
   custody stays outside worker containers.
2. **Containerized workload identity, Phase 2+:** JWT/OIDC when the runtime
   host can provide verifiable workload JWTs. OpenBao JWT auth can verify JWTs
   with local keys or OIDC discovery. This is better than distributing AppRole
   SecretIDs into ephemeral seats.
3. **Kubernetes/OpenShift future:** Prefer JWT auth with short-lived projected
   service account tokens where practical; use Kubernetes auth only when the
   deployment explicitly wants TokenReview integration. OpenBao notes
   Kubernetes auth makes it easy to introduce an OpenBao token into a pod, and
   also points to JWT auth for Kubernetes service account tokens.
4. **Human operator/admin:** OIDC or another human SSO method. Root tokens are
   initialization/break-glass only.

### Audit Configuration

The deployment is invalid for CE until at least one audit device is enabled and
healthy. Recommended minimum:

- local file audit device on the OpenBao host;
- second audit sink to an append-only controller log path or low-volume HTTP
  endpoint when available;
- `log_raw=false`;
- no CE secret values placed in non-string audit fields, because OpenBao's docs
  warn that only JSON strings are HMAC'd by default.

The adapter's `validate_config()` must refuse when:

- `sys/audit` reports no enabled device;
- a configured audit sink is blocked or known unhealthy;
- TLS verification is disabled outside an explicit local-dev profile;
- the CE broker token has broader policy than the ratified profile.

## 6. Secret Path Layout

Use KV v2 for static secret roots and identity metadata that needs versioning.
OpenBao KV v2 uses `data/` and `metadata/` API prefixes for ACLs, so policies
must be written against those prefixes.

Mounts:

- `ce-kv/`: versioned static CE secret and identity documents.
- `ce-transit/`: optional later mount for encryption/signing operations; not a
  first-cut requirement.
- dynamic secret engines: later, only when a concrete target needs them.

Logical paths under `ce-kv`:

```text
identities/dev/<dev-id>/profile
identities/dev/<dev-id>/github
identities/dev/<dev-id>/reviewer
identities/dev/<dev-id>/signing

forge/github-apps/<app-slug>/metadata
forge/github-apps/<app-slug>/private-key
forge/github-apps/<app-slug>/installations/<installation-id>

tokens/bootstrap/<purpose>
tokens/reviewer/<reviewer-id>
tokens/legacy/<source-host>/<opaque-id>

signing/roots/<key-id>
signing/dev/<dev-id>/<key-id>

providers/model/<provider>/<profile>
providers/cloud/<provider>/<profile>

migration/import-manifests/<manifest-id>
migration/decommission/<source-host-id>
```

Policy pattern:

- `ce-broker-read-identity`: read identity metadata needed for seat binding.
- `ce-broker-github-app-mint`: read only the App PEM path and installation
  metadata needed to mint a scoped GitHub App installation token.
- `ce-broker-materialize-runtime-secret`: read only allowlisted runtime secret
  refs for a run, bounded by policy SHA and run id.
- `ce-migration-importer`: create/update migration paths during an approved
  import window; revoked after import.
- `ce-operator-admin`: root/admin operations; human/operator only.
- `ce-seat-direct`: initially empty. Seats should receive materialized grants
  from the broker, not direct OpenBao tokens.

Metadata fields should include:

- `owner_ref`
- `mutation_class`
- `rotation_policy_ref`
- `created_by_ref`
- `created_at`
- `last_rotated_at`
- `source_migration_ref`
- `allowed_purposes`
- `review_by`

## 7. GitHub App Custody and ce-ops#117

OpenBao solves the shared-App custody blocker by making the App private key an
OpenBao-held root secret. The waitlist user or worker seat never holds it.

Flow:

1. CE run is ratified and runtime policy allows a logical secret such as
   `forge.github_app.installation_token`.
2. Broker authenticates to OpenBao with its machine identity.
3. Broker reads `forge/github-apps/<app-slug>/private-key` inside the broker
   process only.
4. Broker mints a GitHub App JWT and calls GitHub's installation-token endpoint
   through the existing `mint_scoped_token` shape or a compatible App-JWT
   runner.
5. Broker returns value-free `MintedCredential` metadata to the orchestrator.
6. The live token is injected only into the authorized forge runner environment
   or socket, never argv.
7. Broker revokes the installation token on completion and records value-free
   revocation metadata.

This preserves the current CE invariant: the installation grant is the mint
ceiling, and CE only emits scoped, time-boxed, per-run credentials.

## 10. P3-Deployment-Gate Design Addenda

ADR-0005 is accepted, but deployment remains blocked. The Operator can pre-ratify
Phase 3 only against the concrete B.1-B.5 gate designs below. B.6 secret
migration is explicitly held and not designed in this branch.

### 10.1 B.1 SECRET-ZERO BOOTSTRAP: Response-Wrapped AppRole SecretID

**Chosen bootstrap:** response-wrapped AppRole SecretID delivery, operator
initiated, broker-unwrapped once at startup.

Concrete startup flow:

1. Operator initializes/configures OpenBao out-of-band and creates a narrow
   `ce-broker` AppRole whose policy can only:
   - read `ce-kv/data/identities/dev/*` value-free identity documents needed by
     the broker;
   - read the specific runtime secret paths allowed for the pilot;
   - call token lookup/renew/revoke-self as needed;
   - read `sys/audit` / health endpoints for audit preflight.
2. Operator creates a single-use SecretID with a short TTL and one use, then
   response-wraps it with a shorter wrapping TTL.
3. Operator starts the broker by injecting only the wrapping token into the
   broker process environment or stdin at startup time. The wrapping token is
   never written to `.env`, `~/.ce-keys`, repo files, shell history, argv, tmux
   send text, dispatch records, or runtime evidence.
4. Broker unwraps the token through its injected OpenBao runner, receives the
   SecretID in process memory, performs AppRole login, immediately zeroes/drops
   the SecretID reference, and keeps only the resulting broker token in memory.
5. Broker records value-free bootstrap metadata: role name, wrapping accessor or
   non-secret correlation ref, unwrap time, broker token accessor ref, TTL, and
   audit ref. It never records RoleID, SecretID, wrapping token, or broker token.
6. Broker refuses to serve any request unless audit preflight passes after login.

Emergency fallback is operator-injected tmpfs SecretID: the Operator writes the
SecretID to a `0600` tmpfs path, starts the broker with a file descriptor or path
ref, the broker reads once and unlinks before accepting requests. This fallback
requires an explicit incident note and is not the steady-state design.

Rejected: durable SecretID in host `.env`, `~/.ce-keys`, repo files, service unit
environment, argv, worker container environment, or agent-visible pane text.

### 10.2 B.2 DEPLOYMENT HOST + TOPOLOGY

**Chosen host/topology for P3 pilot:** controller-owned VPS service on the
CE-DEV-1/CE controller network, not DGX, not a worker container, not public.

Topology:

- OpenBao runs as a controller-owned service with integrated storage for the
  single-node P3 pilot.
- Listener is TLS-only; CE broker validates the server certificate via an
  explicit CA bundle/path in broker config.
- Network exposure is broker-network-only: bind to a private interface or
  localhost plus controlled tunnel from the controller broker; no public
  listener, no direct worker-seat access, no agent-seat token auth.
- OpenBao root/unseal operations are operator-only; broker role is non-root.
- Broker is the only routine CE component allowed to authenticate to OpenBao.
  Worker containers receive only broker-materialized file/env/socket refs.
- P3 does not use HA clustering. HA/raft multi-node topology is a later
  hardening gate after the single-node pilot proves audit and revoke behavior.

### 10.3 B.3 UNSEAL + BACKUP/RESTORE + EMERGENCY REVOCATION

**Unseal method:** Shamir unseal for P3 pilot. Auto-unseal is deferred because it
introduces a second cloud/KMS root-of-trust before the first OpenBao pilot has
proved its own custody model.

P3 unseal posture:

- Operator creates Shamir shares with a threshold chosen in the P3 runbook.
- Shares are stored outside the repo and outside the OpenBao host, with holder
  labels recorded value-free in the runbook.
- Root token is used only for initialization/break-glass, then sealed under the
  operator break-glass procedure; routine broker access uses AppRole/JWT only.

Backup/restore:

- Integrated-storage snapshots are encrypted before leaving the OpenBao host.
- Backup location and encryption key custody are operator-owned and not in repo.
- Restore is tested before any production secret import: restore to an isolated
  OpenBao instance, verify health/audit devices, verify policy/auth mounts, and
  prove a fake/canary secret read with no live secret values.
- Backup evidence records contain snapshot id, digest, timestamp, restore-test
  result, and operator ratification ref only.

Emergency mass revocation / root compromise:

1. Freeze broker issuance and stop worker secret materialization.
2. Revoke broker tokens and all AppRole SecretIDs for `ce-broker`.
3. Disable the broker auth mount if root or broker role compromise is suspected.
4. Revoke dynamic leases and GitHub installation tokens reachable from broker
   audit/grant metadata.
5. Rotate GitHub App private keys and any imported runtime tokens before
   resuming service.
6. Seal OpenBao if host compromise is suspected; preserve audit logs/snapshots
   as incident evidence.
7. Treat non-rotatable signing or attestation material as compromised until a
   separate Operator ratification re-establishes trust.

### 10.4 B.4 BLAST-RADIUS / CO-TENANCY

**Position:** runtime tokens, model-provider keys, bootstrap tokens, reviewer
tokens, and GitHub App PEMs may share the first OpenBao pilot instance under
separate mounts/policies. Signing roots and attestation keys (`ce-root-v1`,
release signing roots, ratification/attestation private keys) must not share
that instance in P3.

Reasoning:

- Runtime credentials are operational, short-lived or rotatable, and can be
  mass-revoked.
- Signing roots and attestation keys define CE evidence authority; compromise
  recovery requires trust re-establishment, not just rotation.
- Co-tenanting both classes would let a runtime secret-plane compromise become
  a governance-root compromise.

Allowed in P3 pilot instance: `forge/github-apps/*`, runtime provider keys,
reviewer/bootstrap tokens selected for canary use, value-free identity metadata.

Forbidden in P3 pilot instance: `ce-root-v1`, release signing roots,
attestation private keys, root ratification keys, or any non-rotatable evidence
authority material. Those require a separate instance or a later mount with
separate operator custody and explicit ratification.

### 10.5 B.5 AUDIT-FAIL-CLOSED VERIFICATION

**Pinned version target:** OpenBao `2.5.5` for P3 verification unless the
controller explicitly re-pins before deployment.

Phase 2 code verification, already in this branch:

- `OpenBaoSecretIdentityBackend.validate_config()` refuses when `sys/audit`
  reports no enabled audit device.
- `issue()` calls audit preflight before returning a grant.
- Tests use injected runners only; no live OpenBao call is possible in CI.

Pre-P3 real-version acceptance test:

1. Start a contained OpenBao `2.5.5` instance with TLS in a disposable
   controller-owned environment.
2. Enable a file audit device and prove a harmless read/login succeeds while
   the audit sink is writable.
3. Block audit writes deliberately, for example by making the audit file path
   unwritable or filling/locking the audit sink in the test container.
4. Attempt a harmless authenticated read/login.
5. Record whether OpenBao refuses the request, blocks, or returns an error when
   audit cannot write. The accepted P3 posture requires a fail-closed outcome;
   any fail-open result blocks deployment and requires an alternate audit sink
   or broker-side refusal before issue.
6. Preserve evidence: OpenBao version, container/image digest or binary digest,
   audit config, command transcript with no secret values, observed HTTP status
   or timeout, and operator ratification ref.

# OpenBao-backed SecretIdentityBackend

## Context and Problem Statement

CE now runs a growing fleet of dev and reviewer seats with unique identities.
The old shared-author credential pattern is retired. Current secrets are
scattered across host-local paths such as `~/.ce-keys`, `~/.hermes/.env`,
per-host GitHub App PEMs, reviewer tokens, and bootstrap tokens. That blocks
portable containerized seats, per-dev identity custody, and the ce-ops#117
shared-App waitlist path because users must not receive the shared App private
key.

## Decision Drivers

- CE needs a central, governed secret store for per-dev identities and App
  custody.
- Secret values must never appear in argv, tmux, evidence, ledgers, or tracked
  records.
- Runtime credentials must be short-lived, least-privilege, auditable, and
  revoked on release.
- The default backend must avoid HashiCorp BUSL lock-in while preserving a
  Vault-compatible API profile.
- The implementation must keep CE's seams small: one adapter, no scattered
  provider calls.

## Considered Options

1. OpenBao self-hosted behind `SecretIdentityBackend`.
2. HashiCorp Vault/HCP behind the same adapter.
3. Infisical.
4. AWS Secrets Manager or GCP Secret Manager.
5. Doppler, 1Password Connect / Secrets Automation, or Bitwarden Secrets
   Manager.
6. Continue host-local secret files with stricter conventions.

Provider comparison:

- **OpenBao:** self-hosted, open-source Vault fork under open governance;
  supports the secret storage, auth, audit, lease, renewal, and revocation model
  CE needs; default because it avoids HashiCorp BUSL dependency and keeps Vault
  compatibility.
- **HashiCorp Vault/HCP:** compatible profile and potential managed/SLA option,
  but not the default because of BUSL/procurement/cost concerns called out in
  ce-ops#113.
- **Infisical:** strong UX and machine-identity story, but the issue research
  summary says dynamic secrets and audit retention are not in the desired
  low-cost/open default profile.
- **AWS/GCP Secret Manager:** good cloud leaf stores for static roots, but not
  the CE-wide identity broker because CE still needs a lease/revoke/audit
  mediator and cross-cloud portability.
- **Doppler / 1Password / Bitwarden:** useful bootstrap or team UX products,
  but primarily static secret distribution for CE's purposes; not sufficient as
  the default governed runtime broker.
- **Host-local files:** rejected as the steady state because they recreate the
  exact scatter, portability, audit, and shared-App custody problem ce-ops#113
  is meant to retire.

## Decision Outcome

Chosen option: **OpenBao self-hosted behind `SecretIdentityBackend`**, because
the operator has already ratified OpenBao as the default backend on ce-ops#113,
OpenBao provides the Vault-compatible secret, auth, audit, lease, and revoke
model CE needs, and the adapter keeps HashiCorp Vault/HCP viable as a managed
compatibility profile without coupling CE to provider-specific calls.

The decision does not authorize a live deployment. It authorizes the design
direction and the next implementation gates: interface/schema substrate,
OpenBao adapter with fakeable I/O, controller deployment pilot, then governed
migration.

## Consequences

- Good: CE gets a central secret plane with audit-before-issue and JIT minting.
- Good: ce-ops#117 can move shared GitHub App custody out of user hands.
- Good: per-dev identities can become portable across hosts/containers.
- Good: HashiCorp Vault/HCP remains compatible through the adapter.
- Bad: CE now operates a sensitive service; backup, unseal, audit, and upgrade
  runbooks become mandatory.
- Bad: AppRole bootstrap is still a secret-custody problem until workload
  identity is available.
- Bad: OpenBao v2.5.x is active and security-sensitive; CE must pin, monitor,
  and test upgrades rather than assuming a frozen Vault API.

## Non-Ratification Statement

This ADR draft records a proposed design. It does not ratify a deployment,
authorize migration of live credentials, approve root/unseal custody, or permit
agent self-access to OpenBao.
